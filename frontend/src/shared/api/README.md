# API фронтенда

Публичная точка входа — `@/shared/api/client`: `apiRequest`, `ApiError`,
`getApiErrorMessage` и тип `ApiRequestOptions`. Она не зависит от Vue или конкретного
тренажёра. Схемы и преобразования принадлежат соответствующей функции приложения.

## Как добавить запрос

1. Опишите используемые поля ответа схемой Zod рядом с API-функцией.
2. Вызовите `apiRequest(path, schema, options)`.
3. Верните из функции проверенные данные в формате, удобном для приложения.
   Преобразование можно сделать через `.transform()` схемы или отдельный mapper.
4. Добавьте тесты корректного ответа, HTTP-ошибки и нарушения контракта.

```ts
import { z } from 'zod';
import { apiRequest } from '@/shared/api/client';

const dialogueSchema = z.object({
  data: z.object({
    id: z.number().int().positive(),
    message: z.string(),
  }),
}).transform(({ data }) => data);

export function startDialogue(topic: string, signal?: AbortSignal) {
  return apiRequest('/api/dialogues', dialogueSchema, {
    method: 'POST',
    json: { topic },
    signal,
  });
}
```

Это пример будущего запроса, а не существующий endpoint.

## Тела запросов и ответы

- Объект JSON передавайте через `json`: сериализация и Content-Type общие.
- Файлы передавайте через `body: formData`. Не задавайте boundary вручную:
  транспорт снимает Content-Type, чтобы браузер выставил его вместе с boundary.
- `body` также поддерживает обычные тела fetch. Для них задавайте нужный
  Content-Type самостоятельно. `json` и `body` взаимоисключающие.
- Заголовки могут быть объектом, `Headers` или массивом пар.
- JSON распознаётся по Content-Type, включая `application/*+json`.
- Пустое тело преобразуется в `undefined`. Если endpoint намеренно ничего
  не возвращает (например, 204), передайте `z.void()`. Для остальных ответов
  обязательна их настоящая схема, не `z.any()`.
- Не используйте `.strict()` без необходимости: добавление неизвестного поля
  бэком не должно ломать клиент. Проверяйте обязательные поля и типы известных
  полей, задавайте defaults только там, где отсутствие действительно допустимо.
- `invalidResponseMessage` позволяет задать понятный текст ошибки контракта
  для конкретного запроса. Техническая причина сохраняется в `error.cause`.

## Ошибки

`ApiError` содержит `kind`, `status` (null без HTTP-ответа), `responseData`
(тело HTTP-ошибки) и `cause`.

- `network`: соединение или чтение ответа оборвалось.
- `http`: сервер вернул неуспешный статус.
- `invalid-response`: HTTP успешен, но JSON или данные не соответствуют схеме.
- `aborted`: запрос отменён.

Для общего сообщения используйте `getApiErrorMessage(error, fallback)`.
Специальные действия зависят от `kind` и `status`, а не от текста сообщения.
Транспорт не показывает уведомления и не изменяет состояние экрана.
Тела ответов, токены и персональные данные не следует писать в логи.

Авторизация сохраняет cookies и один повтор исходного запроса после 401.
Одновременные запросы используют одно обновление сессии. Сам запрос авторизации
не запускает обновление рекурсивно. Для других ошибок автоматических повторов нет:
повтор POST может создать дублирующее событие. Глобального таймаута нет;
передавайте `signal`, если конкретному сценарию нужна отмена. Таймаут интерфейса
голосовой проверки остаётся в логике тренировки и не меняет сетевой контракт.

## Текущие контракты тренажёра

`practiceSchemas.ts` проверяет данные до изменения состояния. Для слова обязательны
только id и непустое слово; остальные поля нормализуются как раньше.
Для обычного ответа нужна булева оценка, для пропуска — подтверждение skip.
Если сервер передаёт success, он должен быть true. Новые поля допускаются.
Совместимость с прежним плоским ответом и полем correct изолирована в схеме.
Подтверждение ручной проверки должно содержать id нужного слова и manual_review.
